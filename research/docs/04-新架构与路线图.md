# 04 · 新架构与路线图：propose → judge → render

## 4.1 管线（三段，职责隔离）

```
页面文本 → [A 候选器 propose] → [B 法官 judge/Jev] → [C 渲染器 render] → 高亮 DOM
              高召回·本地·免费      批量打分·联网·花钱     Top-K·复用老代码
```

- **A 候选器（本地，不调模型）**：`Intl.Segmenter('zh')` 打底 + 老词典做补充，
  目标召回不求准。输出带 offset 的候选 span。失败模式是碎，不碎粘（粘住的搭配 Jev 救不回来）。
- **B 法官（Jev）**：state = 整段原文；questions = 每候选一题 noul（§03.4 wording）；
  每批 20–40 题；返回概率。省钱变体：先对句打分，只给高分句内的词打分（成本降 5–10 倍，首版可不做）。
- **C 渲染器（复用老代码）**：`dom.js` 的收集/替换/观察者逻辑保留，
  把 `segmentation.js` 的「词典+随机」换成「按分取 Top-K」：滑块 30% = 每段前 30% 候选。
  密度从此**稳定**（定义见 01.4 第 2 条）。

## 4.2 成本与延迟账（动手前先算）

- 输入 token ≈ state（段落，几百）+ Q × 指令（每题几十字，Q=20–40）。
  一页 20 段 → 约 20 次请求。可优化：只处理可视区、滚动防抖、按文本 hash 缓存分数。
- 延迟：70–500ms/批（官方量级），段落间可并发 3（专业版并发数），整页秒级内完成，
  比 LLM 整页生成快一个量级，但比纯本地慢——首屏先渲染候选（灰态），分数回来再点亮。
- 风险：并发/限流 429/529 需指数退避；失败时降级为「只断词不高亮」，不断行。

## 4.3 评测：先证明中文可用（不写代码也能做）

建 20–30 段中文语料（新闻/技术/小说各 ~1/3），每段人工标「删掉会损害理解」的词（5–10 个）。
对比四种排序：随机、老词典 POS、Jev noul、（可选）LLM。指标：

1. Precision@K（K=密度，如 30%）：命中的人工关键词比例。
2. 虚词误伤率：Top-K 里「的/了/在/和」占比，越低越好。
3. 延迟/成本实测：每段 token 与耗时记账。

**门槛**：Jev 的 P@K 显著高于随机和老词典，且虚词误伤率低于 10%，才进入实现。
否则走备选：本地 embedding 重排（JevEmbed 这类）或 RLCD 微调小模型——那是另一个文档。

## 4.4 一步步实现顺序（每步可独立驗收）

1. **评测先行**：语料 + 人工标注 + 手工调 Jev（playground 或 curl），输出 P@K 表格 → Go/No-Go。
2. **候选器**：独立 TS 模块 + 单测（固定搭配不切碎、offset 回对原文），无网络。
3. **法官客户端**：批量请求、重试退避、hash 缓存、并发控制；先做脚本版，再进扩展。
4. **渲染替换**：`segmentation.js pushSegment` 换成 Top-K，`dom.js` 管线不动；密度滑块语义改为 K%。
5. **隐私与设置**：API key 存服务端/扩展 storage（不进源码）、联网开关、PRIVACY.md 重写。
6. **灰度**：先只处理正文段落（article/p），信息流、输入框（contenteditable）保持跳过。
