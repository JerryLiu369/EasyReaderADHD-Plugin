# 02 · 老方案病根（对照 `tmp_reader/` 代码）

## 2.1 分词：前向最大匹配 + 词集上限 8 字

`src/content/segmentation.js:62 forwardMaxMatch`：从左到右、最长 8 字、命中词集就切，
否则单字成词。词集来自 `dictionary.js getWordSet`，即本地 JSON 词典 key 的并集。

三个致命点：

1. **无上下文**：「来到北京立方庭参观」能否切对，完全取决于词典里有没有收「立方庭」。
   没收 → 碎成单字；多收 → 长词吞掉短词。中文专名、新词永远在词典外。
2. **错误不可恢复**：下游 `pushSegment`（同文件 :86）只做词典 POS 查找 + 随机密度，
   上游切错下游没有任何纠正机会。
3. **英文分支同样脆弱**：`segmentSpaceBasedText` 按空格切 + 去后缀（-s/-ed/-ing），
   遇到中文标点混排、长词直接失效。

这就是你说的「任何非大模型分词器都太差」——指望一个静态词集解决 Q1（哪里断），中文里注定如此。

## 2.2 重要性：词性 = 重要性，且密度 = 随机

`pushSegment` 的逻辑：`shouldHighlightPos && shouldHighlightByDensity`。

- `shouldHighlightPos`：名词/动词/形容词 → 高亮。等于假设「所有名词同等重要」，
  一段出现 15 个名词就高亮 15 个，主次不分。
- `shouldHighlightByDensity`（同文件 :52）：`Math.random() < density/100`。
  滑块控制的是**期望比例**，具体落到哪些词上是掷骰子。
  用户会看到虚词没高亮算运气好，关键词没高亮也算运气不好——「效果完全不对」的主观来源。

## 2.3 大模型方案为什么也差（你的第二个判断是对的）

- **慢**：自回归逐 token 生成，整页延迟秒级起步，边读边出高亮跟不上滚动。
- **贵**：输出 token 按量计费，而高亮任务的输出（词列表/offset）恰恰很长。
- **效果差**：让 LLM 直接输出「高亮哪些词 + 位置」是生成 + 解析两步，
  span 漂移、幻觉 offset、格式破裂都是常见死法。你要的是**打分**，不是**写字**。

结论：Q2（哪些值得留）是个**判断**问题，不该用**生成**模型做。这正是 Jev 的位置。
